# VinhPhatERP Engineering Rules

## 1. STATUS & PURPOSE

This file is the **mandatory engineering contract** for VinhPhatERP v3.
Every AI Agent and Developer MUST strictly adhere to these rules.

Applicable stack:

- Frontend: React 18, TypeScript, Vite, TailwindCSS (Semantic Tokens), Radix UI / Shadcn
- Backend & Server: Hono, Drizzle ORM, Supabase (PostgreSQL, Auth, RLS, Realtime)
- Data Management: React Query (TanStack Query), Zod
- Testing: Vitest, Playwright E2E

---

## 2. NON-NEGOTIABLE CORE DISCIPLINE

Before modifying any code, the AI Agent MUST:

1. **Read this file** and understand the constraints.
2. **Inspect the target and directly related files** (Follow Scoped Context — do NOT load the entire codebase).
3. **Draft an Impact Map** (Trace: `UI -> Hook -> Service -> API -> RPC -> DB`).
4. **Produce a comprehensive Audit (Phase 1)** before proposing or modifying anything.
5. **Never execute multi-phase refactors in a single turn.** Must stop at each Gate for User Approval.
6. **Never silently weaken, bypass, or comment out a rule or test.**
7. **Never perform speculative or unrelated refactoring.**
8. **Preserve existing business behavior** unless explicitly instructed by the User.

---

## 3. 🚨 ERP SAFETY RULE (CRITICAL)

AI MUST explicitly distinguish between:

- **Code Refactoring**: Restructuring code without altering runtime behavior.
- **Business Behavior Change**: Changing logic, rules, constraints, or calculations.

If a proposed change alters or touches any of the following:

- Pricing / Discounts / Tax calculations
- Fabric roll / Stock quantities / Unit conversions (kg, meters, rolls)
- Customer / Supplier Debt (Công nợ AR / AP)
- Payment status / Invoicing / Cash flow
- Order status flow (e.g. `draft -> pending -> confirmed -> in_production -> ready_to_ship -> completed`)
- Reservation / Allocation / Unreservation concurrency
- Accounting entries or balances
- User permissions / Role authorization / RLS policies

The AI Agent MUST:

1. Explicitly flag the item as **`[BUSINESS BEHAVIOR CHANGE]`** in the audit/plan.
2. Explain the exact operational difference and risk.
3. **STOP IMMEDIATELY** and await explicit user approval before touching code.

## 4. IMPACT MAPPING REQUIREMENT

For any target component or feature, the Agent MUST map the vertical dependency chain:

```text
TARGET COMPONENT
  ↓
UI SUB-COMPONENTS
  ↓
CUSTOM HOOK (State / Orchestration)
  ↓
SERVICE / DOMAIN LOGIC (Pure functions, transforms, math)
  ↓
API CLIENT (`src/api/...`)
  ↓
RPC FUNCTION (`untypedDb.rpc(...)` or `supabase.rpc(...)`)
  ↓
DATABASE TABLE / RLS / TRIGGERS
  ↓
REALTIME / WEBHOOKS / BACKGROUND TASKS
```

If any shared dependency affects multiple features (e.g. Inventory, Orders, Accounting), assess the **Impact Risk**:

- **LOW**: Isolated UI/formatting change.
- **MEDIUM**: Hook or API change within a single feature.
- **HIGH**: Shared service, RPC, schema, or cross-feature transaction -> **Requires strict review**.

## 5. THE 22 ENGINEERING & REFACTORING RULES

### Rule 1: No Duplicate Code

- No duplicated blocks > 10 lines of JSX or > 5 lines of logic.
- Extract common patterns into reusable functions, custom hooks, or shared components (`@/shared/...`).

### Rule 2: String Reuse & Vietnamese Constants

- No hardcoded Vietnamese labels, messages, or error strings repeated ≥ 2 times.
- Centralize into `constants.ts` (e.g., `MESSAGES`, `LABELS`, `STATUS_NAMES`).

### Rule 3: No Business Logic in UI Components

- UI components (`.tsx`) must NOT contain math calculations, array `.reduce()`, complex filters, or inline validations.
- UI components ONLY handle presentation and user interactions.
- Move calculations to `services/` (pure functions) or domain hooks (`useSomething`).

### Rule 4: Centralized Zod Validation

- No manual `if (!value)` or ad-hoc validation routines.
- All form inputs, mutation payloads, and API parameters MUST be validated via Zod schemas (`src/schema/...`).

### Rule 5: Domain-Specific Naming

- Prohibit generic variable names like `data`, `data1`, `temp`, `res`, `obj`, `item2`.
- Use explicit domain naming: `weavingRoll`, `fabricBatch`, `supplierInvoice`, `deliveryTripStop`.

### Rule 6: Database Safety & Idempotency (CRITICAL)

- **FORBIDDEN**: Direct `supabase.from(...).insert(...)` without idempotency.
- **FORBIDDEN**: Generating business IDs using `Date.now()` (use UUID or sequence generators).
- **REQUIRED**: Single-row writes must use `safeUpsert` (`src/lib/db-guard.ts`).
- **REQUIRED**: Multi-table or concurrent operations (stock deductions, debt updates, status transitions) MUST use atomic Postgres RPCs (`FOR UPDATE` locking).
- Check duplicates at application layer before hitting DB constraints.

### Rule 7: Strict Error Handling

- Never swallow errors silently with empty `catch {}`.
- Log errors via structured logger (`console.error('[ModuleError]', err)`).
- Provide clear, user-readable feedback via toasts or error state components.

### Rule 8: Async / Await Discipline

- Every Promise must be properly awaited or handled.
- Prevent race conditions using AbortController, React Query cancellation, or state guards.

### Rule 9: Clean State Management

- No redundant, duplicate, or stale state.
- Lift state up only when necessary; prefer custom hooks or React Query cache over prop drilling.

### Rule 10: Pure Side Effects

- No heavy computations or direct API queries inside `useEffect`.
- Data fetching belongs in React Query hooks (`useQuery`, `useMutation`).

### Rule 11: Component Size & Responsibility

- Components MUST be modular (< 300 lines of code).
- Split large files into container components (orchestration) and presentational components (display).

### Rule 12: Reusability & Shared Modules

- Check `@/shared/` before creating a new component or utility.
- Never write cross-feature relative imports (`../orders/...` into `suppliers/`). Use `@/shared/...` or feature boundaries.

### Rule 13: Performance & Query Optimization

- Zero N+1 queries (no API calls inside loops).
- Eliminate over-fetching and under-fetching.
- Large lists (> 100 items) MUST use virtualization (`TanStack Virtual` / `VPVirtualCombobox`) or pagination.

### Rule 14: Strict Type Safety

- **FORBIDDEN**: `any`, `as any`, `@ts-ignore` (unless documented edge case approved by lead).
- Use proper TypeScript interfaces, generics, discriminated unions, and type guards.

### Rule 15: Clean File & Feature Structure

- Every feature under `src/features/<feature-name>/` follows standard structure:
  - `components/`: Feature UI components
  - `hooks/`: Feature state and query hooks
  - `api/`: API adapters and RPC callers
  - `schema/` or `types/`: Domain types and Zod schemas

### Rule 16: Dependency Cleanliness

- No circular dependencies.
- Respect architecture layers: UI -> Hook -> Service -> API -> DB. Lower layers must never depend on higher layers.

### Rule 17: Semantic Design Tokens (Zero Hardcoded CSS)

- **FORBIDDEN**: Hardcoded hex/rgb/hsl colors in CSS or JSX (e.g., `#ffffff`, `rgba(0,0,0,0.1)`, `text-gray-900`, `bg-red-500`).
- **REQUIRED**: Use semantic design tokens defined in `src/styles/theme/tokens.css`:
  - Text: `text-foreground`, `text-muted`, `text-primary`, `text-danger`, `text-success`
  - Backgrounds: `bg-surface`, `bg-surface-secondary`, `bg-danger-soft`, `bg-success-soft`
  - Borders: `border-default`, `border-muted`
- Must pass `npm run lint:css` with 0 errors.

### Rule 18: Zero Debug Logs in Production

- Remove all `console.log`, `debugger`, and temporary debug dumps before completion.

### Rule 19: Security & RLS Compliance

- Sanitize and validate all user inputs.
- Never bypass Supabase Row Level Security (RLS) policies.
- Never expose sensitive tokens or credentials in client bundles.

### Rule 20: Comprehensive UX & Feedback States

Every data-driven screen or component MUST have:

1. **Loading skeleton** during fetch (no flash of empty or default data).
2. **Error state** with retry action and clear message.
3. **Empty state** when returned arrays are empty (`[]`).
4. **Pending state**: Disable submit/action buttons with spinner while mutating.

### Rule 21: Render Safety & Accessibility (a11y)

- Error guard: `error instanceof Error ? error.message : String(error)`.
- Null guards: `{value ?? '---'}`.
- Stable React keys: `key={item.id}` (NEVER use array index for dynamic/mutable lists).
- Accessibility: Images must have `alt`, interactive elements must use semantic `<button>` or include `role="button"` and `tabIndex={0}`.

### Rule 22: Testing & Regression Guard

- Every extracted service, calculation function, and critical domain hook MUST have unit tests (`.test.ts`).
- Existing tests must remain 100% passing.
- New behavior must be covered by test assertions.

Before any task or phase is considered complete, the following commands MUST pass with **0 errors and 0 warnings**:

```bash

npm run typecheck                 # Verifies TypeScript compiler integrity
npm run lint -- --max-warnings=0  # Verifies ESLint architecture rules
npm run lint:css                  # Verifies Stylelint semantic tokens (0 hardcoded colors)

```
