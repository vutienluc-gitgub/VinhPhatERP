# Review Guard (VinhPhatERP Multi-Axis Quality Gate)

## Overview

Inspired by Addy Osmani's `code-review-and-quality` and `code-simplification`, adapted specifically for **VinhPhatERP v3**.
Every change must be reviewed across five axes before proceeding to Gate 4 (`APPROVE MERGE`).
The standard: **"Code chạy được ≠ Code đúng. Không lỗi ≠ Production-ready."**
Approve a change when it demonstrably improves overall system health, eliminates duplication, and strictly adheres to ERP Architecture Guards.

---

## When to Use

- Before proposing changes to Gate 3 or Gate 4 in `AI_WORKFLOW.md`.
- After implementing or refactoring any feature, custom hook, or UI component.
- When performing a code cleanup or refactoring task under `.agents/rules/refactor-checklist.md`.
- When reviewing code generated by another agent or subagent.

## The Five-Axis ERP Review

### 1. Correctness & Business Invariants

Does the code preserve critical ERP business invariants?

- **Zero unauthorized changes to business behavior**: Are calculations for pricing, VAT, fabric roll conversions (kg $\leftrightarrow$ meters $\leftrightarrow$ rolls), or customer/supplier debt untouched unless explicitly marked `[BUSINESS BEHAVIOR CHANGE]`?
- **Idempotency & DB Safety**: Are writes using `safeUpsert` instead of raw `supabase.insert`? Are multi-table transactions executed via atomic RPC (`untypedDb.rpc(...)`)?
- **Edge cases covered**: Are empty arrays, `null`, `undefined`, zero division, and negative numbers guarded?
- **Error paths**: Are errors caught and exposed to users with friendly Vietnamese messages rather than swallowed silently (`catch {}`)?

### 2. Readability & Code Simplification

Can another engineer follow the code immediately without explanation?

- **Clarity over cleverness**: Are complex nested ternaries or chained callbacks flattened?
- **Domain-driven naming**: No generic variables (`data`, `temp`, `item`, `res`). Use `weavingRoll`, `fabricBatch`, `supplierInvoice`, `customerDebt`.
- **String reuse**: Are Vietnamese strings, status labels, and error messages centralized in constants? (No raw Vietnamese strings repeated $\ge 2$ times).
- **Dead code removal**: No commented-out legacy code, unused imports, or `_unused` variables left in place.
- **Component size limit**: Are components kept $< 300$ lines? Split container/orchestration from presentational components when growing too large.

### 3. Architecture & Guard Compliance (MANDATORY)

Does the change pass the 3-tier Architecture Guard?

- **No Emoji**: Zero emoji characters in code or comments (ESLint rule: `no-emoji`).
- **Semantic Design Tokens**:
  - CSS / JSX MUST use tokens from `src/styles/theme/tokens.css` (e.g. `bg-surface`, `text-foreground`, `text-muted`, `bg-danger-soft`, `text-success`).
  - Strict ban on hardcoded colors: No `#ffffff`, `rgba()`, `text-gray-900`, `bg-red-100`, `border-blue-500`.
- **No Raw Native Select**: Native `<select>` is forbidden. Use `VPSelect` ($\le 30$ items), `VPCombobox` ($> 30$ items), or `VPVirtualCombobox` ($> 500$ items).
- **No Business Logic in UI**:
  - Strict ban on `reduce()`, math calculations, or complex array transforms inside UI components (ESLint rule: `no-business-logic-in-ui`).
  - Move business logic to pure domain services (`src/services/...`) or custom hooks (`use...`).
- **No Cross-Feature Relative Imports**:
  - Features must not import directly from each other (`../other-feature/..`). Use `@/shared/...`.
- **Zod Schema Validation**:
  - All form and mutation inputs must be validated via centralized Zod schemas. No manual `if (!value)` checks.

### 4. Security & Hardening

Does the change prevent data leakage or unauthorized manipulation?

- **Row Level Security (RLS)**: Ensure all direct table reads/writes respect Supabase RLS policies.
- **Input Sanitization**: User inputs must be trimmed and validated before hitting services or APIs.
- **No Secrets in Code**: API keys, service roles, or VAPID secrets must never be hardcoded in frontend files.
- **Safe SQL / RPC**: No raw string concatenation when calling database functions.

### 5. Performance & Render Safety

Does the change avoid lag, memory bloat, or UI flashing?

- **Render Safety**:
  - Stable keys for lists: `key={item.id}` (Never `key={index}`).
  - Null guards: `{value ?? 'N/A'}` or `error instanceof Error ? error.message : String(error)`.
  - Loading skeletons present during async fetching (no flash of default empty state).
  - Empty states displayed when lists return empty arrays.
  - Submit buttons disabled during mutation (`isSubmitting` / `isPending`).
- **Query Efficiency**:
  - No N+1 queries in loops.
  - Virtualization applied for large lists ($> 100$ items).
  - Server-side pagination used for big database tables.

## Structural Remedies (Fix the Design, Not Just the Nit)

When you spot a smell, apply the named remedy:

1. **Replace chained `if/else` on types/statuses** $\rightarrow$ Use a mapping object or status transition table.
2. **Logic repeated $\ge 2$ times** $\rightarrow$ Extract helper function or custom hook.
3. **Repeated inline styling** $\rightarrow$ Extract to a CSS utility class or CVA variant.
4. **Leaking feature logic in shared modules** $\rightarrow$ Relocate logic back to its domain feature folder.
5. **Excessive props passing** $\rightarrow$ Use React Context or co-locate state.
